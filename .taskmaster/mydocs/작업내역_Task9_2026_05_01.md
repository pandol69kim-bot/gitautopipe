## 구현 상세

### 1. 타입 정의 (`src/types/workflow.ts`)

```typescript
type TriggerType = 'event' | 'cron' | 'manual';
type WorkflowStatus = 'idle' | 'running' | 'completed' | 'failed' | 'retrying';
type StepStatus = 'pending' | 'running' | 'completed' | 'failed' | 'skipped';
type ErrorStrategy = 'stop' | 'continue' | 'retry';

interface WorkflowTrigger {
  type: TriggerType;
  event?: string;   // event 타입일 때 이벤트 이름
  cron?: string;    // cron 타입일 때 cron 표현식
}

interface WorkflowContext {
  workflowId: string;
  executionId: string;
  triggeredAt: Date;
  payload?: Record<string, unknown>;
}

interface WorkflowStep {
  id: string;
  name: string;
  execute(context: WorkflowContext): Promise<unknown>;
}

interface Workflow {
  id: string;
  name: string;
  steps: WorkflowStep[];
  triggers: WorkflowTrigger[];
  errorHandling: ErrorHandlingConfig;
}

interface ErrorHandlingConfig {
  strategy: ErrorStrategy;
  maxRetries?: number;
  retryDelayMs?: number;
  notifyOnFailure?: boolean;
}

interface StepResult {
  stepId: string;
  status: StepStatus;
  output?: unknown;
  error?: string;
  startedAt: Date;
  completedAt: Date;
  durationMs: number;
}

interface Execution {
  executionId: string;
  workflowId: string;
  status: WorkflowStatus;
  triggeredAt: Date;
  completedAt?: Date;
  stepResults: StepResult[];
}

interface ExecutionResult {
  executionId: string;
  workflowId: string;
  status: WorkflowStatus;
  stepResults: StepResult[];
  totalDurationMs: number;
}
```

### 2. WorkflowOrchestrator 클래스 (`src/workflows/orchestrator.ts`)

#### 주요 메서드

| 메서드 | 설명 |
|--------|------|
| `registerWorkflow(workflow)` | 워크플로우 등록 + 이벤트 트리거 연결 |
| `getWorkflow(id)` | 등록된 워크플로우 조회 |
| `executeWorkflow(workflowId, payload?)` | 워크플로우 실행 → ExecutionResult 반환 |
| `getExecutionHistory(workflowId)` | 실행 이력 조회 |
| `scheduleWorkflow(workflowId, cron)` | Cron 스케줄 등록 (Map 기반) |
| `getSchedules()` | 등록된 스케줄 전체 조회 |
| `emit(event, payload)` | 이벤트 발행 → 연결된 워크플로우 실행 |

#### 에러 처리 전략

| 전략 | 동작 |
|------|------|
| `stop` | 스텝 실패 시 즉시 중단, 이후 스텝 건너뜀 |
| `continue` | 스텝 실패 후 다음 스텝 계속 실행 |
| `retry` | `maxRetries`만큼 지수 백오프 재시도 (retryDelayMs × 2^attempt) |

#### 설계 포인트

- `EventEmitter` (Node.js 내장) 로 이벤트 트리거 구현 — 외부 의존성 없음
- `randomUUID` (crypto) 로 실행 ID 생성
- 재등록 시 기존 이벤트 리스너 제거 후 재등록 (`removeAllListeners`)
- 실행 이력은 `Map<workflowId, Execution[]>` 에 누적 저장

### 3. 사전 정의 워크플로우

| 워크플로우 ID | 이름 | 트리거 | 에러 전략 |
|--------------|------|--------|-----------|
| `onMissionUpdate` | Mission 업데이트 처리 | event: `mission:updated` | continue |
| `onMeetingSync` | Notion 미팅 동기화 | event: `meeting:synced` | retry (2회, 1000ms) |
| `onSkillUpdate` | Skill/Insight 게시물 배포 | event: `skill:updated` | stop |
| `weeklyDigest` | 주간 다이제스트 생성 | cron: `0 9 * * 1` | continue |

`weeklyDigest`는 생성 시 `scheduleWorkflow('weeklyDigest', '0 9 * * 1')` 자동 등록.

### 테스트 케이스 목록 (29개)

#### registerWorkflow (3개)
- 워크플로우를 등록하고 조회할 수 있다
- 동일 ID로 재등록하면 덮어쓴다
- 등록되지 않은 ID는 undefined를 반환한다

#### executeWorkflow (6개)
- ExecutionResult 구조를 반환한다
- 모든 스텝을 순서대로 실행한다
- 각 스텝에 WorkflowContext를 전달한다
- stepResults에 각 스텝의 결과가 기록된다
- 존재하지 않는 워크플로우 실행 시 에러를 던진다
- payload를 전달할 수 있다

#### getExecutionHistory (3개)
- 실행 후 이력에 저장된다
- 여러 번 실행하면 이력이 쌓인다
- 등록되지 않은 워크플로우 이력은 빈 배열이다

#### errorHandling - stop (3개)
- 스텝 실패 시 status가 failed이다
- stop 전략에서 실패한 스텝 이후 스텝은 실행되지 않는다
- 실패한 스텝의 error가 stepResults에 기록된다

#### errorHandling - continue (1개)
- continue 전략에서 스텝 실패 후 다음 스텝이 실행된다

#### errorHandling - retry (2개)
- retry 전략에서 실패 시 maxRetries만큼 재시도한다
- 재시도 성공 시 status가 completed이다

#### event trigger (2개)
- 이벤트 emit 시 해당 워크플로우가 실행된다
- 다른 이벤트로는 실행되지 않는다

#### predefined workflows (6개)
- onMissionUpdate 워크플로우가 등록된다
- onMeetingSync 워크플로우가 등록된다
- onSkillUpdate 워크플로우가 등록된다
- weeklyDigest 워크플로우가 등록된다
- onMissionUpdate는 event 트리거를 갖는다
- weeklyDigest는 cron 트리거를 갖는다
- 각 사전 정의 워크플로우는 최소 1개의 스텝을 갖는다

#### scheduleWorkflow (2개)
- 스케줄 등록 후 getSchedules에서 조회된다
- 같은 워크플로우 재스케줄 시 기존 스케줄을 교체한다
