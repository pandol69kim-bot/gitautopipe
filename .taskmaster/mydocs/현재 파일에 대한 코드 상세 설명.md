# 현재 파일에 대한 코드 상세 설명

작성일: 2026-05-13  
대상 파일: `src/types/workflow.ts`

---

## 1. 파일의 목적

이 파일은 워크플로우 실행 시스템에서 사용하는 핵심 타입들을 한곳에 모아 둔 타입 정의 파일이다.
실제 비즈니스 로직을 수행하는 구현 코드는 없고, 워크플로우를 구성하고 실행 결과를 표현하기 위한 공통 데이터 계약(contract)을 제공한다.

즉, 이 파일의 역할은 다음과 같다.

- 워크플로우가 어떤 방식으로 시작되는지 정의
- 워크플로우가 어떤 상태를 가질 수 있는지 정의
- 각 스텝(step)이 어떤 구조를 따라야 하는지 정의
- 실행 중 생성되는 컨텍스트와 결과 데이터 구조를 정의
- 에러 처리 정책을 일관된 방식으로 표현

이 타입들이 기준점이 되기 때문에, `src/workflows`, `src/cli`, `src/types`의 다른 모듈이나 향후 오케스트레이션 로직은 이 구조를 기반으로 연결될 가능성이 높다.

---

## 2. 전체 구조 한눈에 보기

이 파일은 크게 아래 3개 층으로 나뉜다.

1. 상태를 표현하는 문자열 유니언 타입
2. 워크플로우 구성 요소를 표현하는 인터페이스
3. 실행 결과와 오류 처리 규칙을 표현하는 인터페이스

흐름으로 보면 다음과 같다.

`WorkflowTrigger` -> `Workflow` -> `WorkflowStep` 실행 -> `Execution`/`ExecutionResult` 생성

## 3. 문자열 유니언 타입 설명

### 3.1 `TriggerType`

```ts
export type TriggerType = 'event' | 'cron' | 'manual';
```

워크플로우가 어떤 방식으로 시작되는지를 정의한다.

- `event`: 특정 이벤트 발생 시 실행
- `cron`: 일정 스케줄에 따라 실행
- `manual`: 사용자가 직접 실행

이 타입이 있으면 트리거 방식을 자유 문자열로 넣는 실수를 줄일 수 있다.
예를 들어 `evnet` 같은 오타를 타입 단계에서 막을 수 있다.

### 3.2 `WorkflowStatus`

```ts
export type WorkflowStatus = 'idle' | 'running' | 'completed' | 'failed' | 'retrying';
```

워크플로우 실행 단위 전체의 상태를 나타낸다.

- `idle`: 아직 실행되지 않음
- `running`: 현재 실행 중
- `completed`: 정상 완료
- `failed`: 실패
- `retrying`: 재시도 중

이 값은 워크플로우 수준의 상태를 나타내므로, 개별 스텝 상태와 구분해서 봐야 한다.

### 3.3 `StepStatus`

```ts
export type StepStatus = 'pending' | 'running' | 'completed' | 'failed' | 'skipped';
```

각 스텝의 상태를 표현한다.

- `pending`: 아직 실행 전
- `running`: 실행 중
- `completed`: 성공적으로 완료
- `failed`: 실패
- `skipped`: 정책 또는 조건에 따라 건너뜀

워크플로우 전체가 `running`이어도 내부 스텝은 각각 다른 상태를 가질 수 있다.

### 3.4 `ErrorStrategy`

```ts
export type ErrorStrategy = 'stop' | 'continue' | 'retry';
```

워크플로우 실행 중 오류가 발생했을 때 어떤 정책을 적용할지 정의한다.

- `stop`: 즉시 중단
- `continue`: 오류가 나도 다음 스텝 진행
- `retry`: 재시도 수행

이 타입은 향후 실행 엔진에서 분기 처리의 기준값으로 사용될 가능성이 크다.

## 4. 인터페이스별 상세 설명

### 4.1 `WorkflowTrigger`

```ts
export interface WorkflowTrigger {
  type: TriggerType;
  event?: string;
  cron?: string;
}
```

워크플로우의 실행 조건을 정의하는 구조체다.

필드 설명:

- `type`: 트리거 방식
- `event?`: `type`이 `event`일 때 사용되는 이벤트 이름
- `cron?`: `type`이 `cron`일 때 사용되는 cron 표현식

특징:

- `event`와 `cron`이 모두 optional 이다.
- 따라서 타입만으로는 `event` 타입인데 `event` 값이 비어 있는 잘못된 상태를 완전히 막지는 못한다.
- 현재는 단순한 데이터 구조 정의에 집중한 형태이고, 실제 유효성 검증은 별도 로직에서 처리해야 한다.

예시:

```ts
const trigger: WorkflowTrigger = {
  type: 'event',
  event: 'github:push',
};
```

---

### 4.2 `WorkflowContext`

```ts
export interface WorkflowContext {
  workflowId: string;
  executionId: string;
  triggeredAt: Date;
  payload?: Record<string, unknown>;
}
```

각 스텝이 실행될 때 공통으로 전달받는 실행 컨텍스트다.

필드 설명:

- `workflowId`: 어떤 워크플로우인지 식별
- `executionId`: 이번 실행 건의 고유 ID
- `triggeredAt`: 실행 시작 시각
- `payload?`: 추가 입력 데이터

의미:

- 각 스텝은 외부 전역 상태를 직접 참조하기보다, 이 컨텍스트를 통해 필요한 입력을 받게 된다.
- `payload`를 `Record<string, unknown>`으로 둔 것은 유연성을 높이는 대신, 실제 사용 시 타입 단언이나 검증이 필요하다는 의미다.

---

### 4.3 `StepResult`

```ts
export interface StepResult {
  stepId: string;
  status: StepStatus;
  output?: unknown;
  error?: string;
  startedAt: Date;
  completedAt: Date;
  durationMs: number;
}
```

개별 스텝 하나의 실행 결과를 표현한다.

필드 설명:

- `stepId`: 어느 스텝의 결과인지 식별
- `status`: 해당 스텝 상태
- `output?`: 실행 결과 데이터
- `error?`: 실패 시 오류 메시지
- `startedAt`: 실행 시작 시각
- `completedAt`: 실행 종료 시각
- `durationMs`: 실행 소요 시간

의미:

- 단순히 성공/실패만 기록하지 않고, 시간 정보까지 같이 보관한다.
- 나중에 리포트 생성, 성능 분석, 장애 추적에 바로 활용할 수 있다.
- `output` 타입이 `unknown`이라서 어떤 스텝이든 결과를 담을 수 있지만, 사용하는 쪽에서 안전하게 해석해야 한다.

주의점:

- 실패한 경우에도 `completedAt`과 `durationMs`를 채우도록 전제하고 있다.
- 즉, 이 구조는 스텝이 끝났을 때의 결과 스냅샷에 가깝다.

---

### 4.4 `WorkflowStep`

```ts
export interface WorkflowStep {
  id: string;
  name: string;
  execute(context: WorkflowContext): Promise<unknown>;
}
```

워크플로우를 구성하는 실제 실행 단위다.

필드 설명:

- `id`: 스텝 고유 식별자
- `name`: 사람이 읽기 쉬운 이름
- `execute(...)`: 실행 함수

핵심 포인트:

- `execute`는 비동기 함수이며 `Promise<unknown>`을 반환한다.
- 즉, 각 스텝은 API 호출, 파일 처리, 동기화 작업처럼 비동기 작업을 수행할 수 있다.
- 구현체는 이 인터페이스를 만족해야 하므로, 워크플로우 엔진은 스텝 구현 상세를 몰라도 일관된 방식으로 호출할 수 있다.

예시 개념:

```ts
const step: WorkflowStep = {
  id: 'sync-notion',
  name: 'Notion 동기화',
  async execute(context) {
    return { synced: true, workflowId: context.workflowId };
  },
};
```

---

### 4.5 `ErrorHandlingConfig`

```ts
export interface ErrorHandlingConfig {
  strategy: ErrorStrategy;
  maxRetries?: number;
  retryDelayMs?: number;
  notifyOnFailure?: boolean;
}
```

워크플로우 오류 처리 정책을 정의한다.

필드 설명:

- `strategy`: 기본 오류 대응 방식
- `maxRetries?`: 재시도 최대 횟수
- `retryDelayMs?`: 재시도 간 대기 시간
- `notifyOnFailure?`: 실패 시 알림 여부

설계 의도:

- 단순히 `retry` 여부만 두지 않고, 재시도 횟수와 지연 시간까지 포함해 확장 가능한 구조를 만들었다.
- 향후 Slack/Notion/이메일 알림 같은 기능과 쉽게 연결할 수 있다.

주의점:

- `strategy`가 `stop` 또는 `continue`여도 `maxRetries`를 넣을 수 있는 구조다.
- 즉, 필드 조합 유효성은 타입 시스템이 아니라 런타임 검증에 의존한다.

---

### 4.6 `Workflow`

```ts
export interface Workflow {
  id: string;
  name: string;
  steps: WorkflowStep[];
  triggers: WorkflowTrigger[];
  errorHandling: ErrorHandlingConfig;
}
```

워크플로우 정의 자체를 표현하는 최상위 구조다.

필드 설명:

- `id`: 워크플로우 식별자
- `name`: 표시용 이름
- `steps`: 순차 또는 정책 기반으로 실행될 스텝 목록
- `triggers`: 이 워크플로우를 시작시킬 조건 목록
- `errorHandling`: 오류 처리 정책

이 타입은 사실상 "워크플로우 설계도" 역할을 한다.
구현체에서는 이 객체를 등록해 두고, 트리거가 발생하면 해당 워크플로우를 실행하는 구조가 자연스럽다.

---

### 4.7 `Execution`

```ts
export interface Execution {
  executionId: string;
  workflowId: string;
  status: WorkflowStatus;
  triggeredAt: Date;
  completedAt?: Date;
  stepResults: StepResult[];
  error?: string;
}
```

특정 워크플로우가 실제로 한 번 실행된 기록을 표현한다.

필드 설명:

- `executionId`: 실행 인스턴스 ID
- `workflowId`: 어떤 워크플로우의 실행인지
- `status`: 현재 또는 최종 상태
- `triggeredAt`: 시작 시각
- `completedAt?`: 종료 시각
- `stepResults`: 스텝별 실행 결과 목록
- `error?`: 전체 실행 관점의 오류 메시지

`Workflow`와의 차이:

- `Workflow`는 정의(definition)다.
- `Execution`은 실제 실행 기록(instance)다.

즉, 하나의 `Workflow`에서 여러 `Execution`이 만들어질 수 있다.

---

### 4.8 `ExecutionResult`

```ts
export interface ExecutionResult {
  executionId: string;
  workflowId: string;
  status: WorkflowStatus;
  stepResults: StepResult[];
  totalDurationMs: number;
}
```

실행이 끝난 뒤 외부로 반환하기 좋은 요약 결과 구조다.

필드 설명:

- `executionId`: 실행 ID
- `workflowId`: 워크플로우 ID
- `status`: 최종 상태
- `stepResults`: 각 스텝 결과
- `totalDurationMs`: 전체 실행 시간

`Execution`과의 차이:

- `Execution`은 진행 중 상태까지 포괄하는 내부 기록 객체에 가깝다.
- `ExecutionResult`는 최종 응답 또는 보고용 DTO에 가깝다.
- `completedAt`이나 `error` 대신, 요약 정보 중심으로 단순화되어 있다.

## 5. 타입 간 관계 정리

### 정의 단계

- `Workflow`는 하나 이상의 `WorkflowStep`을 가진다.
- `Workflow`는 하나 이상의 `WorkflowTrigger`를 가진다.
- `Workflow`는 하나의 `ErrorHandlingConfig`를 가진다.

### 실행 단계

- 워크플로우가 시작되면 `WorkflowContext`가 생성된다.
- 각 `WorkflowStep.execute()`는 이 컨텍스트를 입력받아 실행된다.
- 각 스텝 결과는 `StepResult`로 누적된다.
- 전체 실행 상태는 `Execution`으로 관리된다.
- 최종 반환 시 `ExecutionResult`로 정리될 수 있다.

---

## 6. 이 파일의 설계상 장점

### 6.1 역할 분리가 명확하다

정의(`Workflow`)와 실행 결과(`Execution`, `ExecutionResult`)가 분리되어 있다.
이 구분은 유지보수에서 매우 중요하다.

### 6.2 확장성이 좋다

새로운 트리거 방식, 상태 값, 에러 처리 옵션을 비교적 쉽게 추가할 수 있다.

### 6.3 오케스트레이터 구현에 적합하다

`WorkflowStep.execute(context)` 형태는 워크플로우 엔진이나 orchestrator가 표준 방식으로 스텝을 호출하게 해 준다.

### 6.4 보고/감사 로그 용도로 유리하다

시간, 상태, 에러, 결과를 모두 별도 구조로 남길 수 있어서 리포트 생성과 장애 분석에 적합하다.

---

## 7. 현재 타입 설계의 한계와 주의점

### 7.1 조건부 필드 제약이 약하다

예를 들어 `WorkflowTrigger`는 `type: 'event'`일 때 `event`가 반드시 있어야 하지만, 현재 타입만으로는 강제되지 않는다.

같은 문제가 `ErrorHandlingConfig`에도 있다.
예를 들어 `strategy: 'retry'`일 때만 `maxRetries`와 `retryDelayMs`가 의미가 있는데, 현재는 모든 전략에서 optional 필드로 열려 있다.

### 7.2 `unknown` 사용으로 유연하지만 후처리가 필요하다

- `payload?: Record<string, unknown>`
- `output?: unknown`
- `execute(...): Promise<unknown>`

이 구조는 범용성은 높지만, 실제 사용 시 타입 가드나 스키마 검증이 필요하다.
그렇지 않으면 런타임에서 값 해석 오류가 날 수 있다.

### 7.3 시간 필드가 모두 `Date` 객체 기준이다

직렬화해서 JSON으로 저장하거나 API 응답으로 내보낼 경우 문자열로 변환될 수 있으므로, 저장/전송 계층에서 일관성 있는 처리 규칙이 필요하다.

---

## 8. 예상 사용 시나리오

이 파일은 다음 흐름에서 사용될 가능성이 높다.

1. 개발자가 `Workflow` 객체를 정의한다.
2. 시스템이 이벤트/스케줄/수동 요청을 통해 트리거를 감지한다.
3. 실행 시 `WorkflowContext`를 만든다.
4. `steps`를 순서대로 실행한다.
5. 각 단계 결과를 `StepResult`로 기록한다.
6. 전체 실행 정보를 `Execution`으로 관리한다.
7. 마지막에 `ExecutionResult`를 반환하거나 리포트에 반영한다.

---

## 9. 간단한 예시 해석

아래처럼 어떤 워크플로우가 정의된다고 가정할 수 있다.

```ts
const workflow: Workflow = {
  id: 'daily-report',
  name: '일일 리포트 생성',
  triggers: [{ type: 'cron', cron: '0 9 * * *' }],
  errorHandling: {
    strategy: 'retry',
    maxRetries: 3,
    retryDelayMs: 5000,
    notifyOnFailure: true,
  },
  steps: [
    {
      id: 'collect-data',
      name: '데이터 수집',
      async execute(context) {
        return { ok: true, executionId: context.executionId };
      },
    },
  ],
};
```

이 정의를 실행 엔진이 처리하면:

- 스케줄러가 오전 9시에 트리거 발생
- `WorkflowContext` 생성
- `collect-data` 스텝 실행
- 성공/실패 여부를 `StepResult`에 기록
- 전체 결과를 `ExecutionResult`로 반환

이런 형태의 아키텍처로 자연스럽게 연결된다.

---

## 10. 결론

`src/types/workflow.ts`는 워크플로우 시스템의 구현 코드가 아니라, 그 구현 전체가 의존하게 될 공통 타입 명세 파일이다.

이 파일이 중요한 이유는 다음과 같다.

- 워크플로우 정의 구조를 표준화한다.
- 스텝 실행 인터페이스를 고정한다.
- 실행 결과 기록 형식을 통일한다.
